# Draft security advisory: VULN-1238

**Status:** Draft for security and release review; no published advisory, release version, or release sign-off is implied.

## Vulnerability

Previously, sealed-session authentication trusted decoded JWT payloads without verifying signatures. An attacker knowing the 256-bit cookie password could mint cookies with arbitrary identities and authorization claims. AES-256-GCM cookie integrity itself was not bypassed. Severity: medium because exploitation requires cookie-password compromise.

## Fix

Authenticate access tokens using RS256 and keys fetched from the configured client's environment JWKS. Reject missing/unknown key IDs, incompatible keys, invalid signatures, missing expiration or subject, and tokens not yet valid. Only signature-verified, identity-bound expired tokens signal `needs_refresh`; all verification failures return an unauthenticated state with no identity or authorization claims. Expiration uses zero leeway (`now >= exp` expires), preserving the prior strict expiration policy while correcting its equality boundary. Operators must maintain synchronized clocks.

Cookie `user.id`, when present, must equal the signed JWT `sub`. Impersonation comes only from the signed `impersonator` claim: a cookie impersonator without a matching signed claim is rejected. A signed impersonator is used even if omitted from the cookie. Other user profile fields (including email, email verification, names, and metadata) remain cookie metadata and **must not be used for authorization decisions**. They are not made authentic by this fix if the cookie password is compromised. Applications needing authoritative profile attributes must obtain them from a trusted server-side source.

Keys are cached per client (including clones) for ten minutes. An unknown `kid` forces one cache refresh before rejection. JWKS unavailability fails closed when a key fetch is required; cached keys remain usable within their TTL. The configured API base URL and client ID, not token-supplied URLs, determine the key source. Audience and issuer policy is unchanged: this fix uses client-specific JWKS as the environment trust boundary, not additional issuer/audience checks.

This fix prevents cookie/user.id/impersonator forgery but does NOT provide revocation. A captured JWT remains valid until its `exp`. Mitigations: keep short expiration times, rotate JWKS keys (allowing for cache TTL), and treat expiration as the maximum exposure window for a stolen token. Server-side revocation requires additional infrastructure outside this fix. Rotate compromised cookie passwords and invalidate affected sessions; signature verification does not undo prior compromise or prevent replay of captured, still-valid JWTs.

## Compatibility and release decision

The workspace still declares version **3.4.0**. `authenticate` and `logout_url` become async, and `authenticate_session` now takes a `&Client` first and is async. A configured client ID is required. JWTs without `sub`, and legacy impersonation cookies without signed impersonation claims, now fail closed. Existing deployments must confirm their WorkOS tokens contain the signed claims they rely on. See the draft changelog for call-site migration.

The public API break is approved for local implementation only. Human release owners must approve the breaking-release strategy and version; versioning is deferred to release tooling. Do not ship this workspace as an unreviewed patch release.

## Dependency and validation

Adds exactly pinned `jsonwebtoken = 9.3.1`, MIT-licensed, with default features disabled. It uses the already-present `ring` crypto backend; no second RSA backend or PEM/ASN.1 stack is added. Crate minimum Rust version is 1.73 (SDK minimum 1.88). The prior tree had no JWT verification library.

Regression tests use test-only RSA keys and mock JWKS endpoints. They cover valid signatures and signed claims, captured-token/cookie identity substitution, the complete impersonator matching policy, forged signatures and payloads, unsigned/wrong-algorithm tokens, expiry and required claims, key rotation/cache reuse, and unavailable/malformed keys. Independent security review and release approval remain required.
